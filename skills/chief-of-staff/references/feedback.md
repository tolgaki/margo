# Explicit learning from corrections

Use the feedback and rule records in `work-ledger.md`. The user should be able to inspect why a
rule exists, where it applies, and what changed when it was revoked.

1. Record the specific correction and the relevant work/action revision. Store the reason only
   if the user supplied it. Silence, delay, and a dismissed proposal are not general preferences.
2. Respect "do not learn from this": do not store the correction as a learning example or propose
   a rule from it. The ordinary operational receipt need not claim to be learning.
3. Distinguish one-off instructions from scoped preferences and lasting rules. One short-invite
   edit does not justify shortening every executive communication.
4. Propose a rule only with supporting examples, exact wording, scope, affected routines, and a
   check for conflicts with existing preferences. Do not silently update `preferences.md`.
5. Activate on explicit user confirmation, retain supersession history, and support revocation.
   Revoking a rule does not erase the evidence or change previously sent messages.

Read active scoped rules when drafting or recommending. Explicit current instructions and safety
boundaries still win. No learned rule may grant permission to send, broaden a standing grant,
lower an approval requirement, or convert an inferred obligation into a confirmed one.

For material preference changes, show the exact proposed settings diff as well as the ledger
record. The personal file remains authoritative for the user's base configuration.
