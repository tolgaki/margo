# Margo.Cloud.State.Core: porting notes

Ports `skills/chief-of-staff/scripts/margo_store.py` (as `StateStore`, the name `cloud/README.md`
uses) and provides the Python-compatible helpers every
later state port must use so that `margo-state SCRIPT.py ...` is indistinguishable from
`python3 SCRIPT.py ...`. Reference behaviour is **CPython 3.13** (measured on 3.13.16) and its
`sqlite3`, `json`, `argparse`, `datetime`, `pathlib` and `textwrap` modules.

### Writing a port

1. One `sealed class XScript : IStateScript` per Python script, `ScriptName => "x.py"`, public
   parameterless constructor, in the port's own project. `margo-state` finds it by reflection.
2. `Run` returns `StateScripts.RunGuarded(() => Main(...), stderr)`. Build the parser with
   `new PyArgumentParser(ScriptName, Doc, ...)` and the exact same arguments, help strings and order
   as the Python parser (help text and usage wrapping are compared).
3. Map every `except (...)` clause to the matching C# exception types (`StateError` first if the
   Python code distinguishes it, then `PyOSError`, `PySqliteError`, `PyValueError`, `PyTypeError`,
   `PyKeyError`). Anything else must escape, as it does in Python (exit 1).
4. Print with `PyIO.Print(stdout, PyJson.Dumps(...))` using the script's exact options, for example
   `work_state.py`: `PyJson.Dumps(result, indent: 2, ensureAscii: false, allowNan: false)`;
   `task_state.py`/`memory_state.py`: `StateStore.CanonicalJson(result)`; `proactive_state.py`:
   `PyJson.Dumps(v, indent: 2, sortKeys: true, ensureAscii: false, allowNan: false)`.
   `json.dump(rows, sys.stdout, indent=2)` has no trailing newline: use `PyIO.Write`.
5. Add scenarios under `cloud/contracts/state/<script>/` for every subcommand and failure path,
   then run `python3 tools/state_parity.py --check`, and list the folder in `cloud/contracts/state/README.md`.
6. Use the helpers above for Python's dynamic semantics (`PyNode`, `PyObj`, ...). When one is missing, add it here
   with a CPython-measured test instead of keeping a private copy. A library that the scripts cannot reach gets a
   probe pair: the Python reference in `cloud/contracts/state/probes/`, the C# twin (`IStateProbeScript`) in
   `Margo.Cloud.State.Probes`, never in the port's own assembly.

## argparse coverage

Positionals and optionals; several option strings with `dest`; `nargs` `None`, `?`, `*`, `+`, `N`,
`...`; `choices` (strings); `type=int` (Python `int()`, value is a `BigInteger`) and `type=float`;
`required`; `default` (string defaults are converted at the end, as in Python); actions `store`,
`store_const`, `store_true`, `store_false`, `append`, `append_const`, `extend`, `count`, `help`;
required subparsers with `dest`, `help` and aliases; long-option prefix abbreviation and ambiguity;
`--opt=value`; combined single-dash flags; `--`; negative-number arguments; usage, help sections
and `HelpFormatter`/`RawDescriptionHelpFormatter` wrapping at `COLUMNS - 2` (80 when not a terminal);
error text `prog: error: ...` with the usage on stderr and status 2; `-h` on stdout with status 0.

Not ported because no state script uses them: mutually exclusive and argument groups, `parents`,
`fromfile_prefix_chars`, `parse_intermixed_args`, `version`, `BooleanOptionalAction`, `deprecated`,
non-string `choices`, `metavar` tuples, `exit_on_error=False`.

## sqlite3 semantics kept

- `isolation_level` legacy control: `BEGIN <level>` before INSERT/UPDATE/DELETE/REPLACE when in
  autocommit (statement kind found after skipping whitespace and comments, as CPython's
  `lstrip_sql`; `WITH ... INSERT` is not DML, as in Python); DDL and SELECT never open a transaction.
- One statement per `Execute` (`You can only execute one statement at a time.`), null characters
  refused, `executemany` only for DML, `executescript` commits a pending transaction first.
- Binding: None/bool/ints (int64 range, else `OverflowError`)/floats/str (lone surrogates raise
  `UnicodeEncodeError`)/bytes; other types raise `Error binding parameter N: type 'dict' is not
  supported`. JSON scalars are unwrapped. Reading: INTEGER -> long, REAL -> double, TEXT -> string
  (strict UTF-8), BLOB -> byte[], NULL -> null.
- `rowcount` (-1 for non-DML), `lastrowid`, `in_transaction`, `commit`/`rollback` no-ops outside a
  transaction, `close()` leaves the engine to roll back, `sqlite3.Row` name lookup is
  case-insensitive and a missing name raises `IndexError`.
- Error classes from the primary result code (`IntegrityError` for constraints, `OperationalError`
  for busy/locked/readonly/cantopen..., `DatabaseError` for corrupt/not-a-database); messages are
  `sqlite3_errmsg()`.
- `commit()`, `rollback()` and `executescript()` end an open transaction whatever `isolation_level`
  is (also `None`), as CPython 3.13's legacy control does.

## Deliberate deviations (and why)

1. **Python version.** Behaviour is CPython 3.13 (argparse `options:` heading and usage wrapping,
   `json` "Illegal trailing comma" errors, `fromisoformat` accepting the extended formats). Older
   Pythons that desktop Margo may run (3.9+) word some errors differently. The parity judge always
   compares against the local `python3`.
2. **Rows are read eagerly.** `Execute` steps the statement to completion; Python steps lazily.
   Not observable for the helpers' statements (no row-producing statement has side effects after
   its first row); it avoids holding read locks across caller code.
3. **SQLite build.** The engine is SQLitePCLRaw's bundled `e_sqlite3` (2.1.13), not the system
   `libsqlite3` CPython links (3.45.1 here). Logical state (schema SQL, rows, pragmas, error texts)
   is identical; byte-level page layout and FTS internals may differ, which is why the judge dumps
   databases logically and skips FTS/R-tree shadow-table rows.
4. **Linux only.** Private-mode, owner and link-count checks use `statx`, `open(O_EXCL|O_NOFOLLOW)`,
   `mkdir`, `link` and `fsync` through `libc`; other platforms raise `PlatformNotSupportedException`.
   Margo Cloud runs in Linux containers. (Python also checks modes only on POSIX.)
5. **Recursion limits.** CPython's JSON depth limit comes from the C recursion counter: 9998 nested
   containers decode/encode, 9999 raise `RecursionError`; a Python-level `object_pairs_hook` costs two
   more levels (so `parse_json` accepts objects nested 9996 deep). The C# port uses these measured
   constants, with iterative (stack-safe) parsing and encoding. Other CPython builds may differ by a
   few levels.
6. **Uncaught exceptions** print `Traceback (most recent call last):` and `Type: message`, not a
   Python stack. Exit status 1 and non-empty stderr match, which is what the judge compares.
7. **Undecodable stdin** raises `UnicodeDecodeError` (a `ValueError`, so the scripts' handlers exit
   2 as in Python). `sys.stdin.read()` matches CPython exactly (reason and absolute byte positions; state
   consolidation). `sys.stdin.read(n)` (no port uses it yet; `task_state.py` and `memory_state.py` will) decodes
   chunks of `max(8192, n)` bytes as `TextIOWrapper` does, but where a chunk ends depends on how much a pipe read
   returns, so a position reported for a later chunk can differ from CPython's when the writer is slow.
8. **`RuntimeError`** from `expanduser()` (unknown user, or a `HOME` that still starts with `~`) is
   an `InvalidOperationException` with Python's message; `StateScripts.RunGuarded` reports it as
   `RuntimeError`.
9. *(Withdrawn in the state consolidation.)* `os.link` and `os.replace` errors now name both paths, as
   Python's `str(exc)` does.
10. **`textwrap`/help widths** count UTF-16 units; all help text is ASCII.
11. **Missing namespace attributes** raise `PyTypeError` (Python: `AttributeError`); ports check
    `PyNamespace.Has` where Python uses `hasattr`.
12. **`state_core_probe.py`** (`StateCoreProbeScript`) is not a Margo command: it lets the judge test the shared
    helpers byte for byte. Its twin lives in `Margo.Cloud.State.Probes` (state consolidation; it used to ship in this
    assembly), which `margo-state` references only in builds with `MargoStateProbes=true` and runs only with
    `MARGO_STATE_PROBES=1`. Its Python reference lives in `cloud/contracts/state/probes/`.

## JSON recursion budget

CPython's JSON scanner counts the C recursion levels it uses, and so does every call it makes; how much budget a
call site has left decides more than the container limit. With B the call site's budget (`PyJsonLoadOptions.MaxDepth`:
9998 for `json.loads` called from Python code, `PyJson.MaxDepth`; two less per C-to-Python re-entry on the way, for
example 9996 inside a generator resumed by a C loop) and n the containers open where something happens, measured
with CPython 3.13.16 (`StateCoreFixTests`, `JsonRecursionBudgetTests`, `core/json_recursion_budget.json`,
`helpers/json_recursion_budget.json`):

- a container opens while n + 1 <= B, else `RecursionError` "... while decoding a JSON array/object from a unicode string";
- the default `parse_constant` for `NaN`/`Infinity`/`-Infinity` (a C method) needs n + 1 <= B;
- a Python hook (`object_pairs_hook` at the closing object's own level, `parse_constant`) needs n + 2 <= B to be
  called and n + 3 <= B to raise its own exception (`parse_json`'s duplicate-key and non-finite `StateError`s);
- a decode error built in C (`raise_errmsg` creates `JSONDecodeError`, whose `__init__` is Python code) needs n + 4 <= B;
- "Expecting value" (a `StopIteration` turned into the `JSONDecodeError` after the scan) and the 4300-digit
  `ValueError` need n + 1 <= B; otherwise CPython raises `RecursionError` with the note
  `Normalization failed: type=StopIteration|ValueError args=<unknown>` (part of `Message` here, the last traceback line in Python);
- the `RecursionError` text names the call that ran out: " while calling a Python object" for a C call
  (`_PyObject_MakeTpCall`, C methods), nothing for entering a Python frame;
- errors raised by Python code after the scan (`Extra data`, the BOM check) are unaffected; the first event in
  document order wins.

## Review fixes (second pass)

An independent review compared the first port with CPython 3.13 and fixed these differences, each
with a failing test (`PythonDriftTests`) and, where a command shows it, a parity scenario
(`core/margo_store_unicode.json`, `core/probe_unicode.json`, `core/probe_io.json`):

- `_safe_directory` compared `ToLowerInvariant()` names; Python uses `casefold()`, so a
  `ſhared`/`cloudﬆorage`/`BOX ſYNC` directory was accepted by C# and refused by Python.
- `PyRepr.IsPrintable` and `int()` used .NET's Unicode 16 tables (Python 3.13: 15.1), so `repr()`
  printed new characters raw and `int()` accepted new digits; `validate_timestamp`'s regex `\d` did
  not match astral digits that Python's `re` matches (a different error message).
- `PyPath.Join("/", "x")` returned `//x` (`--state-dir /` gave `//<hash>/margo.sqlite3`).
- `~name` used `$HOME` for the current user and failed for other users; Python reads the password
  database. A `HOME` of `~x` now raises `RuntimeError` as in pathlib.
- `connect()` cast every `margo_meta` key to string: a NULL or BLOB key crashed C# where Python's
  `dict()` simply keeps it.
- `PyConnection.Commit/Rollback/ExecuteScript` did nothing with `isolation_level=None` while a
  transaction was open; CPython commits/rolls back.
- `initialize_config` wrote through a `FileStream` and `read_json` read through one: write and read
  errors (ENOSPC, EFBIG, EIO) escaped as `IOException` (exit 1, and SIGXFSZ killed the process
  leaving the staging file) instead of the `OSError` paths ("configuration unavailable", "cannot read
  valid JSON from ..."). `margo-state` now ignores SIGXFSZ like CPython.
- Undecodable argument and environment bytes became U+FFFD (an init could save a different account,
  or create a differently named file, where Python fails); they are now surrogate escapes, paths are
  encoded with `surrogateescape`, and stderr uses `backslashreplace`.
- OSError subclass names (`TimeoutError`, `BlockingIOError`, ...) were missing from `PythonType`.
- The judge compared only whether stderr was empty, so a different error message passed. It now also
  compares the line the hosted tool reports (`tools/state_parity.py` `reason()`).

### Where the copies differed

The kept behaviour is the one that matches CPython 3.13.16; each difference was checked against CPython.

1. **Deep copies.** Proactive's `Py.Copy` recursed (a stack overflow before the deepest JSON `PyJson` accepts) and fell
   back to `JsonNode.DeepClone`; Work's iterative `Clone` also fell back to it for unexpected values; Memory's was
   iterative and complete. Kept: iterative, never `DeepClone` (`PythonValueCopyTests`).
2. **`dict(x, **kw)` with key/value pairs.** Memory raised the `StateError` "value must contain finite JSON data" at
   the first pair whose key is not a string; Work's `Update` (now `PyNode.DictWith`) reads every pair first, as
   CPython's `dict()` does, so a later unhashable key raises `TypeError` and a pair of the wrong length `ValueError`.
   Kept Work's; `memory/consolidation_dict_pairs.json` (through `MemoryStore._resolve_work_sources`) fails on the build
   before the consolidation.
3. **`str.isspace()`.** `PyRepr.IsSpace` used .NET's categories (Unicode 16); Memory used a table generated from
   CPython. They agree for every code point today (no whitespace was added after Unicode 15.1); kept the generated
   table so a future .NET cannot drift. `re`'s `\w` is `str.isalnum()` or `_` for every code point (checked), so
   Memory's `\w` table and Helpers' `isalnum()` table were one table.
4. **`repr()` of ints beyond 4300 digits.** Work's `PyDynamic.Repr` printed every digit; Proactive's and Memory's raise
   the `ValueError` CPython raises (`PyJson.IntStr`). Kept the latter. Not reachable through the commands: JSON input
   is limited to 4300 digits and stored ints are 64-bit.
5. **Comparisons.** Proactive's `Py.Eq`/`Compare` treated NaN as equal to itself and greater than every number, and
   Work's `CompareNumbers` raised `TypeError` for two strings; Helpers' `PyObj` follows `float_richcompare` (every
   ordering with NaN is false, `==` is false) and compares strings by code point. Kept `PyObj`. Not reachable through
   the commands (SQLite stores NaN as NULL; Work compares validated numbers).
6. **`list.sort` for `PySortedKeys`.** Work's own `count_run`/`binarysort` approximated the merge phase for 64+ keys;
   the Helpers' complete `listsort` port replaces it, so that approximation is gone (`SortedKeyTests`: 602 CPython
   texts still match).
7. **The JSON recursion budget.** Helpers' `PyJsonLoad` re-walked the valid prefix after `PyJson.Loads` and always
   said "while calling a Python object"; CPython says so only when the call that ran out is a C call (for decode errors
   at n = B - 3 and n = B) and says plain "maximum recursion depth exceeded" when entering a Python frame
   (n = B - 2, B - 1). The model is now part of the decoder and exact for both (measured).
8. **`json.loads` of a stored BLOB.** Work's `Loads` raised `TypeError` for bytes; Proactive's (kept as `PyNode.Loads`)
   decoded them as strict UTF-8. Neither is what `json.loads(bytes)` does (detected encoding, `surrogatepass`); see
   "Review of the state consolidation". Only a hand-edited database holds such a value.

### Reviewer findings fixed here

Each has a test that failed on the build before the fix (`StateCoreFixTests`, `PythonValueCopyTests`) and, where a
command shows it, a parity scenario that failed against that build:

- **`validate_timestamp` of a JSON list or dict** raised `TypeError: not a scalar`; it now raises Python's
  `StateError` "timestamp must be an ISO-8601 datetime with an explicit timezone". The Proactive and Memory
  workarounds are gone.
- **`timedelta` range:** totals in (-1000000000 days, -999999999 days) were accepted; CPython raises
  `days=-1000000000; must have magnitude <= 999999999`.
- **Undecodable stdin** always reported "invalid start byte" at a position relative to the `StreamReader` buffer;
  `PyIO.StdinReader` now models `TextIOWrapper` (deviation 7). The Helpers' `PyProcess.ReadStdin` is gone.
- **`JsonNode.DeepClone` on Python values:** replaced everywhere by `PyNode.Copy`; the guard test scans every
  `Margo.Cloud.State*` source and the state tests.
- **`PyJson.Loads` near the nesting limit** modelled only the container limit, so every port except the Helpers
  answered decode errors, `NaN`, failing hooks, "Expecting value" and over-long ints near the limit with the
  ordinary error where CPython raises `RecursionError` (`core/json_recursion_budget.json`: `work_state.py source` and
  `import-preview`).
- **`int()` stripped U+001C..U+001F** (`PyRepr.Strip`, `str.isspace()`), where CPython strips only ASCII whitespace
  after mapping non-ASCII spaces to `' '`, so `int("\x1c5")` is a `ValueError` (`core/int_whitespace.json`:
  argparse `type=int` through the probe and `work_state.py item-update --revision`). `float()` was already right.

### Review of the state consolidation

An independent review re-ran the differential checks against CPython 3.13.16 on inputs the consolidation had not
tried: every code point for `str.isspace()`/`isdecimal()`/`isdigit()`/`isalnum()`/`isprintable()`, `re`'s `\w`,
`strip()`, `unicodedata.decimal()` and `casefold()` (all equal); 400 random `int()` literals with the whitespace and
digit characters around U+001C..U+001F; about 550 undecodable stdin payloads through `capacity.py`, `proactive_state.py`
and `work_state.py`; 500 documents nested 9988-10001 deep through `work_state.py`, `capacity.py` and
`teams_feedback.py`; 9000 comparison and 9000 `ops` cases and 90 sort traces through `helpers_probe.py`; 100 random
proactive scenarios with one column of every table hand-edited to an odd SQLite value. One defect was found and fixed:

- **`json.loads` of a BLOB** (`PyNode.Loads(byte[])`, now `PyJson.LoadsBytes`/`PyIO.DecodeJsonBytes`) decoded the bytes
  as strict UTF-8. CPython decodes them with `json.detect_encoding` and `surrogatepass`: a UTF-8 signature, UTF-16 and
  UTF-32 (with or without BOM) load; `ED A0..BF xx` passes through as a lone surrogate; errors name the detected codec
  (`'utf-16-le' codec can't decode byte 0x7d in position 4: truncated data`, positions after a UTF-8 signature relative
  to it) and a second BOM is "Expecting value", not the `str` BOM error. `JsonBytesTests` (186 CPython measurements;
  63 failed before the fix; a further 40000 random byte strings agree) and `proactive/blob_values.json` (a payload BLOB
  in 13 encodings and damaged forms through `queue-list`) failed on the consolidated build.

## Open questions

- `PyNode.DictWith` cannot hold a key that is not a string (a `JsonObject` cannot): it raises the `StateError` that
  `canonical_json` would raise once every pair has been read. A library caller that uses such a dict before
  `canonical_json` (for example `_resolve_work_sources` reading `ref["ref"]` of a reference written as pairs) sees that
  `StateError` where Python raises a `KeyError` or a later `StateError`. Python's callers pass normalised data.
- `os.getcwd()` is `Directory.GetCurrentDirectory()`: a working directory whose name is not UTF-8
  would be decoded with U+FFFD rather than surrogate escapes (the hosted tool always runs in an ASCII
  scratch directory).
- Strings that Python holds as two lone surrogates forming a valid pair cannot be told apart from the
  astral character in UTF-16; nothing in the helpers produces them.

- Should desktop Margo pin a minimum Python (3.13) so both implementations share error texts?
- The judge skips FTS shadow-table rows; MemorySearch should confirm FTS query results match
  through scenarios instead.
- `PyConnection` uses the SQLitePCLRaw layer that Microsoft.Data.Sqlite ships rather than
  `SqliteCommand`, because Python semantics (implicit `BEGIN`, positional `?` binding,
  one-statement rule, error classes) need statement-level control. Ports can still use
  Microsoft.Data.Sqlite directly for anything outside the state commands.
